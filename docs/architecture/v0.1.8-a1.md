# DWM v0.1.8-a1 – første grense mellom GUI og motor

## Omfang

Denne deltaen er første, **bakoverkompatible** steg. Eksisterende CustomTkinter-GUI,
startskript, batchkjøring og analysemoduler endres **ikke**. `version.py` settes
til `0.1.8-a1` for å markere utviklingsserien.

Ny `app/application_api.py` gir et GUI-uavhengig Python-grensesnitt for:

- Åpne og lagre eksisterende `.n5jobs` (uten formatmigrering).
- Liste jobber med status og alle separate lagringsroller, inkludert beregnet
  effektiv Work-operations-sti.
- Velge aktiv jobb og kontrollere kollisjoner i outputmapper.
- Kjøre én jobb synkront via eksisterende `A39JobRunner` med eksplisitt
  godkjenning av omkjøring/fortsettelse.
- Motta trådsikre hendelser via `poll_events()` og be om kooperativ stopp.

Det finnes ingen import fra `gui`, `tkinter`, `customtkinter`, `PySide6` eller
`PyQt` i den nye API-modulen. Alle GUI-klienter kan bruke den samme kontrakten.

## Lagring

Jobbens `source_root`, `source_extraction`, `work_root`, `work_content`,
`work_operations`, `archive_root` og `output_root` kopieres ikke, flyttes ikke
og omdefineres ikke. Eksisterende `.n5jobs` er autoritativ for lagringsrollene.
Effektiv DWM-utdatasti beregnes fra eksisterende
`app_work_subfolder` og jobblistens `output_subfolder_rule`, men skrives ikke
tilbake over `work_operations`.

Det opprettes **ikke** automatisk en ny katalogmodell eller manifest i a1.
Det er planlagt for a2, etter at gjenfinning, identiteter og sti-regler er
kartlagt og testet mot de eksisterende resultatene.

## Kontrakt for andre GUI

```python
from app.application_api import DwmApplication

app = DwmApplication()
view = app.open_job_list(r"C:\DWM\jobbliste.n5jobs")
for job in view.jobs:
    print(job.job_id, job.status, job.effective_work_operations)

# Kjøring skal gjøres fra GUI-ets arbeidstråd, ikke fra Tk/Qt-eventløkken.
# app.run_job("JOB-001", allow_rerun=False)
# GUI-tråden kan hente status via app.poll_events().
```

### Event-kontrakt

`joblist.opened`, `joblist.saved`, `job.selected`, `run.started`, `run.state`,
`run.progress`, `run.log`, `run.finished`, `run.error`, `run.cancel_requested`.
GUI skal konsumere hendelser på sin egen eventtråd. API-et starter ingen
bakgrunnstråder på egen hånd.

## Workshopkontroll

1. Pakk deltaen over et rent, lokalt repo som står på tag `v0.1.7`.
2. Kjør `test.bat` (hele den eksisterende testpakken + nye a1-tester).
3. Kjør `py tools\dwm_api_smoke.py "C:\sti\til\eksisterende.n5jobs"`.
4. Kontroller at alle Source-/Work-/AIP-stier vises som forventet.
5. Kjør eksisterende `start.bat` og gjennomfør den vanlige GUI-røyktesten.

`dwm_api_smoke.py` er **kun lesende**, og kopierer ikke uttrekk eller
skriver om jobblisten.

## Avgrensninger / risiko

- a1 ombygger **ikke** dagens GUI og løser derfor ikke ennå problemer med
  vindusplassering eller skjermskalering. Det er et bevisst sikkerhetsvalg.
- Den nye applikasjonsfasaden er første API-implementasjon; dagens GUI er ennå
  ikke koblet til den. Dette er arbeid for neste deltrinn.
- Kun kjøring av én jobb er eksponert; full batch-funksjonalitet ligger fortsatt
  i den eksisterende runtime inntil API-et får samme sikkerhetskontroller.
- `run_job` har ikke egen fullstendig run overview/PREMIS-orchestrering som
  GUI/CLI har i dag. Bruk derfor **ikke** den nye API-fasaden til
  produksjonskjøringer før denne integrasjonen er ferdigstilt og verifisert.
- Det er ikke utført fysisk Windows GUI-test i utviklingsmiljøet her.
